## BUG-001 并发新增重名用户产生重复数据

| 项 | 内容 |
|---|---|
| 模块 | 用户管理 |
| 严重程度 | 致命 |
| 优先级 | 高 |
| 状态 | 新建 |
| 关联用例 | TC-CONC-001（补充测试用例.xlsx） |

**前置条件**：以 admin 登录，持有有效 token；系统不存在用户名 `verify_dup`。

**重现步骤**
1. 准备两条完全相同的新增用户请求：`POST /system/user`，Body 均为 `{"userName":"verify_dup","nickName":"复现","password":"Test123456","deptId":103,"status":"0"}`；
2. 使用并发工具（JMeter 2 线程 / Promise.all）**同时**发出这两条请求；
3. 查询用户列表 `GET /system/user/list?userName=verify_dup`，并查库 `SELECT * FROM sys_user WHERE user_name='verify_dup'`。

**预期结果**：唯一性约束生效，仅一条请求成功，另一条提示"登录账号已存在"，数据库中只有 1 条记录。

**实际结果**：两条请求**均返回** `{"code":200,"msg":"操作成功"}`，数据库中出现 **2 条同名记录**（user_id 144、145）。

**证据**：第一次响应 code=200；第二次响应 code=200；数据库 `(144,'verify_dup'), (145,'verify_dup')` 共 2 条。

**根因分析**：`checkUserNameUnique` 唯一性校验与 `INSERT` 之间无锁、无事务隔离，且 `sys_user.user_name` 无唯一索引，存在竞态窗口，并发下双双通过校验后各自插入。

**修复建议**：① 对 `sys_user.user_name` 添加唯一索引（根本手段）；② 新增时加分布式锁或将"校验+插入"置于同一事务并捕获唯一键冲突。

## BUG-002 并发新增重名角色产生重复数据

| 项 | 内容 |
|---|---|
| 模块 | 角色管理 |
| 严重程度 | 致命 |
| 优先级 | 高 |
| 状态 | 新建 |
| 关联用例 | TC-CONC-003（补充测试用例.xlsx） |

**前置条件**：以 admin 登录；系统不存在角色名"验证角色"。

**重现步骤**
1. 准备两条相同的新增角色请求：`POST /system/role`，Body 均为 `{"roleName":"验证角色","roleKey":"verify_role","roleSort":9,"status":"0","menuIds":[1]}`；
2. 并发同时发出两条请求；
3. 查询 `GET /system/role/list?roleName=验证角色` 并查库 `SELECT * FROM sys_role WHERE role_name='验证角色'`。

**预期结果**：仅一条成功，另一条提示"角色名称已存在"，库中仅 1 条。

**实际结果**：两条均返回 `code=200`，库中出现 **2 条同名角色记录**。

**根因分析**：与 BUG-001 同源，`sys_role.role_name` 无唯一索引，唯一性校验存在竞态。

**修复建议**：对 `sys_role.role_name` 添加唯一索引。

## BUG-003 后端缺失用户名长度校验

| 项 | 内容 |
|---|---|
| 模块 | 用户管理 |
| 严重程度 | 严重 |
| 优先级 | 高 |
| 状态 | 新建 |
| 关联用例 | TC-USER-013 / TC-BND-001（功能/补充） |

**前置条件**：以 admin 登录。

**重现步骤**
1. 绕过前端页面，直接调用 `POST /system/user`；
2. Body 中 `userName` 传 **1 个字符**（`"v"`），其余必填项合法：`{"userName":"v","nickName":"1位用户名","password":"Test123456","deptId":103,"status":"0"}`；
3. 观察响应，并查库确认。

**预期结果**：用户名长度规则为 2–20 位，1 位应被拒绝，提示"用户名称长度必须介于 2 和 20 之间"。

**实际结果**：返回 `{"code":200,"msg":"操作成功"}`，数据库成功写入 1 位用户名记录。

**证据**：`sys_user` 表中曾存在 `('v','1位用户名')` 记录（复现后已清理）。

**根因分析**：长度校验（2–20 位）仅在前端表单规则中实现，后端 `SysUserController.add` 只校验唯一性，未校验长度，绕过前端即可写入非法数据。

**修复建议**：后端补充用户名长度校验（服务端校验 + 数据库约束双保险）。

## BUG-004 后端缺失密码长度校验

| 项 | 内容 |
|---|---|
| 模块 | 用户管理 |
| 严重程度 | 严重 |
| 优先级 | 高 |
| 状态 | 新建 |
| 关联用例 | TC-USER-014 / TC-BND-002 |

**前置条件**：以 admin 登录。

**重现步骤**
1. 直接调用 `POST /system/user`；
2. Body 中 `password` 传 **4 位**（`"1234"`）：`{"userName":"v_pwd4","nickName":"4位密码","password":"1234","deptId":103,"status":"0"}`；
3. 观察响应并查库。

**预期结果**：密码长度规则为 6–20 位，4 位应被拒绝，提示"密码长度必须介于 6 和 20 之间"。

**实际结果**：返回 `code=200 操作成功`，数据库成功写入该用户（user_id 147，密码已正常 bcrypt 加密）。

**证据**：`sys_user` 表中存在 `(147,'v_pwd4','4位密码')`。

**根因分析**：密码长度校验仅在前端，后端未校验，可写入弱密码，降低账户安全性。

**修复建议**：后端补充密码长度（及强度）校验。

## BUG-005 后端缺失密码非法字符校验

| 项 | 内容 |
|---|---|
| 模块 | 用户管理 |
| 严重程度 | 严重 |
| 优先级 | 高 |
| 状态 | 新建 |
| 关联用例 | TC-USER-015（功能测试用例.xlsx） |

**前置条件**：以 admin 登录。

**重现步骤**
1. 直接调用 `POST /system/user`；
2. `password` 传含反斜杠的非法字符（`12345\`）：`{"userName":"v_illegal","nickName":"非法字符","password":"12345\\","deptId":103,"status":"0"}`；

**预期结果**：前端规则为"密码不能包含非法字符：< > \" ' \\ |"，该密码应被拒绝。

**修复建议**：后端补充密码字符黑名单校验，与前端规则保持一致。

## BUG-007 新增角色不传 menuIds 返回 500 异常

| 项 | 内容 |
|---|---|
| 模块 | 角色管理 |
| 严重程度 | 轻微 |
| 优先级 | 低 |
| 状态 | 新建 |
| 关联用例 | TC-API-ROLE-002（接口测试用例.xlsx） |

**前置条件**：以 admin 登录。

**重现步骤**
1. 调用 `POST /system/role`，Body 不包含 `menuIds` 字段：`{"roleName":"验证角色2","roleKey":"verify2","roleSort":9,"status":"0"}`；
2. 观察响应。

**预期结果**：返回明确的参数校验提示（如"菜单权限不能为空"）或按默认空权限处理。

**实际结果**：返回 `{"code":500,"msg":"Cannot read the array length because \"<local4>\" is null"}`，为未处理的空指针类异常，错误信息对调用方不友好。

**根因分析**：后端对 `menuIds` 未判空即读取数组长度，抛出底层异常并直接透传给调用方。

**修复建议**：对 `menuIds` 判空处理，返回友好的参数校验提示。

## BUG-008 登录密码 HTTP 明文传输

| 项 | 内容 |
|---|---|
| 模块 | 登录 |
| 严重程度 | 一般 |
| 优先级 | 中 |
| 状态 | 新建（环境整改项） |
| 关联用例 | TC-SEC-005（补充测试用例.xlsx） |

**前置条件**：系统部署于 HTTP（未启用 HTTPS），未开启若依密码加密传输。

**重现步骤**
1. 抓包（Fiddler/浏览器 Network）登录请求 `POST /login`；
2. 观察请求体中 `password` 字段。

**预期结果**：密码应加密传输，或整体走 HTTPS。

**实际结果**：`password` 以明文传输（实测明文即可成功登录，本环境 `http://localhost:8888`）。

**根因分析**：本地测试环境为 HTTP 且未启用密码加密传输配置，属环境/部署问题，非代码缺陷。

**修复建议**：生产环境启用 HTTPS；如需更高安全等级，可启用若依的密码加密传输配置。

## BUG-009 字典类型为空提示文案不准确

| 项 | 内容 |
|---|---|
| 模块 | 字典管理 |
| 严重程度 | 轻微 |
| 优先级 | 低 |
| 状态 | 新建 |
| 关联用例 | TC-DICT-004（功能测试用例.xlsx） |

**前置条件**：以 admin 登录。

**重现步骤**
1. 调用 `POST /system/dict/type`，`dictType` 传空：`{"dictName":"验证字典","dictType":"","status":"0"}`；
2. 观察响应提示。

**预期结果**：提示"字典类型不能为空"。

**实际结果**：返回 `{"code":500,"msg":"字典类型必须以字母开头，且只能为（小写字母，数字，下滑线）"}`——拦截本身生效，但空值场景下命中的是格式校验文案，与场景不符。

**根因分析**：空值校验与格式校验顺序/优先级问题，空值先命中了格式正则提示。

**修复建议**：优化校验顺序，空值时优先返回"字典类型不能为空"。

## 汇总说明

- **共性根因 1（BUG-003~006）**：长度/格式/字符校验只在前端，后端无对应校验，绕过前端即可写入非法数据——属体系性安全弱点，建议后端统一补齐参数校验。
- **共性根因 2（BUG-001/002）**：唯一性校验与插入无锁、无唯一索引，并发下产生重复脏数据——建议数据库层加唯一索引兜底。
- **所有缺陷均已二次独立复现，并经数据库落库核验，非自动化脚本误报。**
- **复现所产生的测试数据已全部清理，数据库无残留。**
